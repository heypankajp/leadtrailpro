## 1. Product overview

### 1.1 Purpose

LeadTrailPro is a web (and later mobile) sales-management application for a staffing/recruitment business. It manages leads from first prospecting through client conversion, records every interaction, links client email activity, supports collaboration and tasks, offers AI-assisted summaries and guidance, manages sales targets, and gives management reporting. (BRD §1)

### 1.2 Goals

1. One system of record for leads, interactions, documents, and candidate profiles.
2. A daily "Action Center" that tells each Sales Manager what to do today.
3. Measurable activity (calls, emails, visits, leads, conversions) against per-person targets.
4. Full accountability: ownership, approvals, archive, and configuration changes are audited.
5. Admin-maintained configuration (dropdown values, roles, targets, security) without code changes.

### 1.3 Technology direction (BRD §1)

React frontend, Node.js backend, responsive web experience, Android and iPhone support, Google Workspace/Gmail integration. The current implementation is a Next.js 16.4.3 application (React 19 on the client, Node.js route handlers on the server) backed by PostgreSQL, packaged with Docker for development and production, and verified by lint, type checks, a production build, and a Selenium browser suite (SPEC §2.3 and §12). Native mobile apps are out of scope for the current phase; the web UI is responsive.

## 2. Users and roles (BRD §2)

| Role | Description | Core permissions |
|---|---|---|
| **Sales Manager** | Owns and works leads | Create and own leads; update own leads; add interactions, tasks, comments, voice notes; transfer own leads to another Sales Manager or Admin (since November 6, 2026 reassign any lead, OWN-03); collaborate; view personal targets, follow-ups, and performance |
| **Recruiter** | Supports leads with candidate work | View leads and add notes/comments; otherwise read-only unless an Admin grants more |
| **Admin** | Full administrative and sales capability | Everything a Sales Manager can do, plus user administration, role display names, reporting for everyone, targets, queued-lead approval, archive management, list-of-values management, device authorization, security configuration, reassignment |

**ROLE-01** (Implemented) The system has exactly three underlying roles: Sales Manager, Recruiter, Admin.
**ROLE-02** (Implemented) An Admin can rename the display name of any role without changing its permissions.
**ROLE-03** (Implemented) An Admin can grant a specific account extra privileges beyond its role defaults (for example, letting a Recruiter create leads). This realizes "unless explicitly permitted by an Admin-controlled rule".

## 7. Assumptions, dependencies, and open questions

1. **Device identification.** Standard browsers cannot read a MAC address. Device authorization needs either a managed-device identifier (MDM), a native/mobile wrapper, or a registration token per browser. Decision pending.
2. **Email delivery.** The Google Workspace SMTP credentials supplied on October 22, 2026 were never verified, and `MAIL_PROVIDER=stub` kept every email feature working by recording messages in the Settings outbox. Findings of October 31, 2026: the development network now reaches smtp.gmail.com on ports 25, 465, and 587, and Google refuses an account password over SMTP (`534 5.7.9 Application-specific password required`); only an App Password (2-Step Verification on) or OAuth is accepted. The project owner is setting up one Google account to serve SMTP, the Maps key, and the Gmail OAuth client. Until its App Password is in `SMTP_PASSWORD`, `MAIL_PROVIDER=stub` remains the safe setting; `npm run mail:test` (SPEC §2) checks a mailbox without the app. Decided on November 6, 2026: no SMTP. Email goes out through the Google app (Gmail API) from a mailbox an administrator chooses under Settings → Email delivery; report emails stay behind a switch, off by default; no passwords are stored, so reset and two-factor emails no longer exist with Google sign-in. Until Google verifies the app the sending mailbox's token expires after seven days while the consent screen is in Testing. Resolved later on November 6, 2026: the consent screen was published (In production, unverified), so that seven-day expiry no longer applies (open question 3).
3. **Google Workspace.** OAuth sign-in and Gmail linking share one Google Cloud OAuth client (project `leadtrailpro`, created November 4, 2026) and one callback. Sign in with Google was built on November 5, 2026: PKCE, the verified Google email matched to a pre-registered account (AUTH-01), and, by the project owner's decision of the same day, read-only Gmail requested in the same consent so that every user's mailbox link exists from the first sign-in and can serve later features or role changes. The accounts come from a seed file (administrator and role accounts, kept out of git) and afterwards from Admin → Users, so there is no self-registration. Accepted consequences: Gmail read-only is a restricted scope, so until Google verifies the app only the consent screen's listed test users can sign in at all (External user type; up to 100), and refresh tokens issued while the screen is in Testing expire after seven days, after which the Emails tab asks to reconnect; verification for a restricted scope includes a third-party security assessment when the app serves people outside the owner's Workspace. The callback URI was registered on November 5, 2026; still to do: enable the Gmail API and list the testers as test users. Also decided on November 5, 2026: sign-in is Google-only wherever the client is configured; the password form, the login API, and the Change password menu entry are off there, and password sign-in survives only for stacks without a client, such as the browser test suite. Resolved on November 6, 2026: the consent screen was published (External, In production, unverified), so test users are no longer needed and refresh tokens no longer expire after seven days; each person sees Google's unverified-app warning at the first consent, and at most 100 people can accept it until Google verifies the app. The Gmail API is in use for sending, the Emails tab, and the mailbox watch.
4. **External data sources.** Indeed, company careers pages, Glassdoor, and Google reviews have their own terms; the BRD scopes these to "when lawfully/technically available".
5. **Business calendar.** Resolved: Admins keep the public-holiday list under Settings → Business calendar. Weekends and listed holidays are non-working days for "yesterday" in reports, target scaling, and natural-language dates.
6. **Native mobile.** Android/iPhone support is met by the responsive web app for now; native apps (camera capture, push) are Phase 3.
7. **Usage time.** "Application usage/time where measurable" requires client-side activity tracking that is not yet defined.
8. **Sales Trip Planner baseline.** The change note of October 21, 2026 says it amends an existing Sales Trip Planner requirement and asks that previously approved requirements be preserved, but neither BRD/SRS version contains a feature of that name. §3.22 treats the change note plus BRD §16/§17 as the whole requirement until the client provides the original planner specification.
9. **Company search and distance provider.** Searching companies by address and radius needs a geocoding and places provider (for example Google Places, which needs billing and limits how long results may be cached), and the driving-minutes radius needs a routing or isochrone service on top. Business types such as "Bakery / Food Manufacturing" do not map to a single provider category and need keyword rules. Provider, budget, and terms are undecided. Status: a Google Maps adapter (Geocoding, Places Text Search, Place Details, Distance Matrix) is written behind the provider interface and used when `MAPS_API_KEY` is set; it has not been exercised against a real key. October 31, 2026: Google Maps Platform bills per API with a monthly free allowance per SKU (about 10,000 calls for the Essentials SKUs the adapter uses) but requires a billing account with a card even for that allowance; the classic Places and Distance Matrix endpoints are marked legacy in favour of Places API (New) and Routes. No-card alternatives reviewed: Geoapify (free plan, 3,000 requests a day, geocoding, places, details, and route matrix on OpenStreetMap data), OpenRouteService (routing and geocoding only), and the public OpenStreetMap services for development. Their business coverage for industrial companies is thinner than Google's; a language model cannot replace geocoding or routing but could assist company discovery. Checked on Google's pricing pages on November 4, 2026: per-SKU free monthly allowances since March 1, 2025 (Essentials 10,000, Pro 5,000, Enterprise 1,000 billable events; billing must be enabled on the project). The adapter's four calls map to Geocoding (10,000 free), legacy Places Text Search (5,000 free, then USD 32 per 1,000), legacy Place Details with contact fields (5,000 free, then USD 17 per 1,000 plus data SKUs), and legacy Distance Matrix (10,000 free elements). The legacy Distance Matrix API can no longer be enabled on Google Cloud projects created after October 2026, and the project `leadtrailpro` is new, so on November 4, 2026 the adapter was moved to the current services: Places API (New) text search with the contact fields in one call (Enterprise SKU, 1,000 free calls a month, each returning up to 20 companies, in place of one Place Details call per company) and the Routes API route matrix for drive minutes (10,000 free elements a month); geocoding is unchanged. The mappers are unit-tested against responses shaped like Google's documentation; the live calls were run with the real key on November 6, 2026 and passed after one fix (the Geocoding API needs the key as a query parameter). November 6, 2026 (later): a key was created and put in `.env.local`; the app now meters every Google call per SKU and calendar month (SPEC §10.8 usage meter), refuses calls past the monthly budgets under Settings → Google Maps usage (defaults 90% of the free allowance), and notifies administrators at 80% and 100%; Google's free allowance is per SKU and resets monthly, and per-API daily quota caps in the Cloud console plus a Billing budget alert are recommended as the hard guarantee. Decided in practice on November 6, 2026: Google Maps Platform (Geocoding, Places API (New), Routes) is the provider, held under the free allowances by the usage meter (NFR-12); the Docker development stack uses it by default. Still to set in the Cloud console: the quota caps and the billing alert.
10. **Job listings source — closed October 26, 2026.** Decision: several sources combined behind one lookup with a per-company cache, free tiers first and the paid Indeed source last, each within a call budget set by the Admin (SPEC §7.13; built). Sources: Adzuna (free developer key), JSearch on RapidAPI (free tier), Indeed through HasData (paid beyond 100 calls a month), plus any custom JSON source. The Government of Canada Job Bank was checked and dropped: its open dataset carries no employer names, its search feed is reserved by its terms for people, and its XML feed is for job boards only. What the client still provides: the three keys and, after a half-day comparison on ten known hiring companies, the decision whether the paid Indeed plan is needed at all. History of the decision — October 25, 2026: Indeed through HasData's Indeed Jobs Scraper API (hasdata.com/apis/indeed-api). Indeed itself offers no public job-search API; HasData is an independent service that returns Indeed search results and job pages as JSON over a key-authenticated HTTPS call (details and the adapter design in SPEC §10.8). What the client should know before go-live: (a) HasData states that it reads publicly available data, that Indeed's terms may restrict automated access, and that compliance is the customer's responsibility; the client accepts that position by choosing this source. (b) Pricing is per request: 10 credits per Indeed call; the free tier gives 100 calls a month, the Startup plan about 20,000 for USD 49, Basic 100,000 for USD 99 (prices on the pricing page; the landing page quotes slightly higher figures). A trip of 50 companies costs up to 50 calls, so Startup covers roughly 400 trip runs or a mix of trips and daily Opportunity searches each month. (c) The API searches by keyword and location, not by company, so the planner will search the company name near the trip address and keep only listings whose company matches (SPEC §10.8); this and the regional `domain` value for ca.indeed.com are to be confirmed on the free tier before the plan is bought. Still needed from the client: a HasData account and API key, the plan, and the acknowledgement in (a). **Alternatives reviewed on October 25, 2026 (to discuss):** scraping Indeed ourselves is not recommended (Cloudflare bot protection, Indeed's terms and robots rules, proxy and maintenance cost, risk of blocking the office IP). Equivalent Indeed-through-a-vendor options: Apify's Indeed scrapers (about USD 2–5 per 1,000 results, roughly USD 5 of free credit a month), same compliance position as HasData. Official, free-tier sources that overlap Indeed without using it: Adzuna API (free developer key, 250 calls a day and 2,500 a month, many boards aggregated, "Jobs by Adzuna" attribution required; Canada coverage and a per-company filter to confirm), JSearch on RapidAPI (Google for Jobs, which indexes many Indeed postings; about 200 free requests a month), the Government of Canada Job Bank RSS feeds, and company career pages (poor coverage for small industrial employers).
